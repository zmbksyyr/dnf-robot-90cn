# 多后端适配平台计划

## 目标

将 `dnf-robot` 维护为一个支持多个服务端实现的平台：调度、Actor 生命周期、机器人公共行为、运行时管理和 Web 管理共用；原生端、S4A21 以及未来的其他模拟端通过各自的适配实现接入。

第一目标是接入 `ServerS4A21`。本计划不要求一次性重写现有系统，也不引入通用插件市场、跨数据库模型或没有实际复用证据的抽象。

## 统一业务意图

后端之间不需要拥有相同的协议、PVF 格式、数据库结构或操作顺序；需要统一的是机器人的业务意图和运营策略。公共层应尽量复用已经验证的机器人逻辑，包括：

- 角色名称生成、名称模板和唯一性策略
- 角色职业/成长选择和批量建号节奏
- 装备筛选、装备套装优先级、强化范围和穿戴策略
- 时装/装扮成套选择和槽位策略
- 喊话模板、频道选择、变量填充和发送间隔
- 目标在线数量、批量上线速率、重连、失败重试和清理策略
- 城镇/副本任务编排、状态跟踪和调度节奏
- 机器人运行状态、审计、指标和 Web 展示模型

这些策略不应因为接入新后端而复制一份。后端适配层负责把本端的 PVF、角色列表、物品定义和协议结果翻译为公共模型，并把公共意图编译成该后端实际需要的封包序列。公共策略只在确实依赖后端事实时读取能力或标准化目录，不直接读取具体 opcode、PVF 原始文本或数据库字段。

可以把边界概括为：

```text
公共业务策略
    -> 标准化角色/装备/地图/能力模型
    -> 后端协议工作流和封包投影
    -> 服务端状态
```

协议流程可以不同，步骤顺序也可以不同；只要最终满足同一个公共业务目标，就不要求各后端共享相同的状态机实现。反过来，后端差异不能改变公共策略的基本语义，例如喊话频率、在线目标数量和装备套装选择不能因为换端而悄悄失效。

## 固定约束

- 环境由 Web 显式选择，启动时不根据路径、进程、端口或操作系统自动猜测并切换。
- 切换环境会停止机器人和会话，备份并重新初始化 robot runtime/config，再启动目标环境。
- 原生端当前仅支持 Linux，现有补丁、密钥、MySQL、`df_game_r` 和外围服务逻辑保留在原生适配边界内。
- S4A21 以及未来模拟端不得直接读取或写入游戏数据库，不区分 SQLite、MySQL 或其他存储实现。
- 模拟端账号、角色、装备、库存和货币变更只能通过对应服务端协议完成。
- 调度层和 Web 层只依赖契约与能力快照，不依赖具体后端包，不散落后端名称判断。
- 新增或删除某个后端时，公共调度和 Actor 层应保持可编译、可测试。
- 尚未实现的能力保留稳定接口并返回明确的占位结果，不允许伪装成成功或静默忽略。

## 分层方案

保持现有项目分层，仅在确有边界的位置增加适配契约：

```text
foundation / shared
        -> backend contracts
        -> capability / actor
        -> protocol primitives and backend protocol implementations
        -> composition
        -> scheduler
        -> entry / webadmin
```

后端实现按垂直边界组织，而不是把所有差异塞进一个公共包：

```text
backend/
  contract/       # 接口、环境信息、能力、端点和不支持结果
  registry/       # 注册和构造当前可用后端
  native/         # 原生 Linux 服务端
  sim_a21/        # S4A21 模拟端
  sim_<future>/   # 后续模拟端
```

协议公共封包、校验和加密继续复用现有 `internal/protocol/dnf`。只有经验证存在差异的登录、角色、动作或副本处理才放入对应后端协议目录；没有差异的实现保持共用。协议层输出的结果应尽量转换为公共事件和状态，不把某个后端的原始封包结构上推到调度层。

## 后端契约

契约只覆盖调度器实际需要的能力，初期包括：

- 环境元数据和支持的操作系统
- Game/Channel/Party 等端点
- 登录准备、账号/角色协议流程
- 缓存失效和服务健康检查
- 邮件、市场、组队等可选外围能力
- 能力快照和明确的不支持结果

契约不得暴露模拟端数据库句柄、数据库路径或 SQL 操作。原生端已有的 MySQL 登录准备也应逐步收拢到 `backend/native`，避免通用调度层继续持有原生 SQL 假设。

契约中的角色、装备、装扮、地图和喊话数据应是公共语义模型。每个后端可以拥有自己的解析器和协议 DTO，但必须在适配边界完成转换；调度器不为每种 PVF 格式编写分支。

### 未实现能力的占位契约

能力接口要覆盖公共调度可能调用的稳定操作，即使某个后端当前还不支持该操作。后端应返回统一的结构化占位结果，至少包含：

- `unsupported` 状态
- 后端标识和操作标识
- 稳定错误码 `backend_capability_unsupported`
- 面向日志和 Web 的原因文本
- 是否可以稍后重试或需要切换后端的建议

占位结果不是成功结果，也不应触发扣费、状态推进、在线计数确认或重试风暴。调度器按操作类型决定跳过、降级、记录待办或停止当前任务；Web 使用同一结果显示禁用原因。未来补齐能力时，只替换后端实现，不改变公共调用方的接口。

## 环境选择与切换

增加持久化的当前环境选择和配置代次。Web 提供：

- 可用后端列表
- 当前后端、根目录、端点和运行状态
- 支持的能力及禁用原因
- 显式切换操作和切换结果

切换流程固定为：校验目标配置 -> 停止 Actor/会话/调度 -> 保存审计和备份 -> 重建目标 runtime/config -> 构造后端 -> 初始化公共组件 -> 启动调度。切换不能静默迁移游戏数据，也不能复用另一后端的密钥、PVF 或状态文件。

## S4A21 第一阶段范围

S4A21 适配只通过网络协议与服务端交互：

1. 建立 Game/Channel 登录和角色选择流程。
2. 验证协议是否提供账号和角色创建路径；若缺失，记录为服务端协议能力缺口，不以改库绕过。
3. 接通进城、移动、喊话和基础重连。
4. 按协议能力逐步接入装备、商店、交易、组队和副本动作。
5. 对不提供的 Auction、Point、原生登录修复等功能返回明确的不支持状态。

S4A21 适配代码不得依赖其整合包使用的数据库类型，也不得读取 `inventory.db` 或其他服务端数据库文件。

### 阶段 4：S4A21 协议适配

- 增加 S4A21 bundle 和必要的协议实现。

- 接通登录、选角、进城、移动、喊话和重连测试。
- 提交：`feat: add s4a21 protocol backend`

### 阶段 5：公共策略迁移和能力矩阵

- 将现有名字、装备/装扮、喊话模板、在线目标、间隔、重连和失败重试策略迁移到与后端无关的公共服务。
- 增加 PVF 标准化目录接口；native 和 S4A21 分别解析自己的 PVF，再提供相同的角色、物品、地图和副本查询语义。
- 将公共调度动作接入 backend contract，由后端把意图转换为各自的协议工作流。
- Web 根据能力快照禁用不支持功能并显示原因。
- 完成协议建号/建角能力验证；缺口保留为显式错误。
- 提交：`feat: route robot scheduling through backend capabilities`

#### 阶段 5.1：拆分 robot 自有状态与原生游戏查询

- 现有 `scheduler/repository` 同时访问 `d_starsky` robot 表和 `taiwan_cain` 原生游戏表，并依赖 MySQL 专用的 `SHOW COLUMNS`、`information_schema` 和原生清理 SQL。
- 在 S4A21 启动装配前，先抽出调度真正需要的 robot-owned 状态契约（身份、建号批次、位置快照、在线状态和商店状态）。
- 第一批拆分范围固定为：机器人目录快照、robot UID/CID 关联、位置快照、在线/运行状态、建号批次状态和 robot-owned 商店状态。
- `AllocateRobotIDs`、角色名唯一性、角色/装备修复、原生角色清理以及任何 `taiwan_cain`/`d_taiwan` 查询不属于通用 robot store；它们保留在 native backend，S4A21 通过协议实现或返回占位错误。
- `RobotLocations` 和位置写入只能读写 robot-owned 位置快照；不能为了模拟端复用 `d_starsky.Dummylist` 与原生角色表的 JOIN。
- 验收标准：S4A21 启动路径不创建原生 MySQL 连接、不执行原生 schema/清理 SQL，仍能维护建号批次、在线目标和城镇位置快照。
- 原生后端继续提供现有 MySQL repository 实现；S4A21 只使用 robot-owned store，绝不把模拟端数据库作为查询或写入目标。
- 不在这一阶段复制完整 repository，也不把原生游戏表改造成通用表；只迁移已被公共调度契约实际使用的 robot 状态。
- 提交：`refactor: separate robot state from native game repository`

### 阶段 6：600+ 批量建号和公共城镇行为

- 复用现有角色生成、名称、装备和装扮策略，通过 S4A21 协议完成 600+ 机器人账号/角色准备。
- 建号队列与在线调度分离，避免建号阶段占满在线会话。
- 接通城镇移动、喊话、在线数量维护、重连和清理。
- 城镇移动必须使用当前后端 PVF 解析出的城镇区域和可移动几何；调度只消费统一的 `MapCatalogItem`，不得读取后端原始 PVF 字段。
- 城镇移动验证通过后，才进入下一阶段的副本工作流；本阶段不实现地下城入口、组队或技能释放。
- 提交：`feat: provision and schedule s4a21 robots`

阶段 6 验收证据（2026-09-23）：真实 `DfoServer.exe` 回归已覆盖登录、城镇坐标移动、跨区域移动、区域喊话和运行时位置确认；600 会话回归、S4A21 自有 PVF 城镇目录解析、Linux/Windows 构建和全量 Go 测试均通过。后续若未补齐新的真实协议证据，不得把地下城、组队、技能或战斗标记为阶段 6 的隐含能力。

阶段 6 删除能力补充（2026-09-23）：S4A21 已通过真实端完成“创建临时角色 -> `GET_USERINFO mode=2` 获取当前名册 -> `DELETE_CHARACTER` -> 再登录确认角色不存在”的协议回归。删除前复用公共 cleanup-pending 与 Actor drain，会话关闭后才进入 adapter；成功 ACK 后只删除 robot-owned state，不直接访问 SQLite/MySQL。由于服务端删除会压缩 slot，adapter 每次都以服务端新下发名册中的角色名解析当前 slot，不使用建号时缓存的旧 slot。

### 阶段 7：地下城工作流与功能扩展

阶段 6 收口补充（2026-09-23）：模拟端的 Web 子进程现在携带明确的 backend 身份；原生数据库、RSA、Party/邮箱内存兼容补丁、市场和原生 PVF 诊断均留在 native 边界内。S4A21 Web 只展示自身 PVF/robot 状态，原生专属接口返回 `backend_capability_unsupported`，不支持的按钮按 capability 置灰。该收口不改变城镇移动、喊话、建号和在线调度，也不提前开放地下城能力。

- 在城镇移动稳定后，按 S4A21 实际协议能力接入地下城入口、组队、技能释放，再扩展商店和交易等功能。
- 地下城移动必须与入口状态机、组队和技能状态一起验证；仅有 `MOVE_MAP` 编解码不能标记为已支持。
- 原生 Linux 运行、部署和现有功能回归。
- Windows/Linux S4A21 运行验证。
- 每个独立功能按主题单独提交，不合并无关重构。

当前最小目标调整为“机器人加入队伍后跟随队长完成地下城房间移动”。只实现该目标所需的组队身份、队长房间通知和跟随移动闭环；技能释放、战斗、结算、奖励、主动回城和 rejoin 继续保留稳定接口并返回 `backend_capability_unsupported`。不为了未来功能预建通用地下城引擎。

#### 阶段 7.0：S4A21 地下城只读协议实验（当前阶段）

- 只读取服务端源码、协议日志和真实端回包，建立单角色普通地下城的证据链。
- 先确认 `ENTER_SELECT_DUNGEON -> SELECT_DUNGEON -> START_MAP -> FINISH_LOADING`，再确认单角色 `MOVE_MAP`；不接入生产调度、不改变能力矩阵。
- 每一步记录请求体边界、服务端前置状态、成功/拒绝回包和断线清理结果；静态 parser 结果与真机观察必须分开标记。
- 选择、入场费用、加载释放、房间身份或回城任一环节证据不足时，继续保持 `backend_capability_unsupported`。
- 阶段出口：形成可复现的单角色协议样本和失败样本；只有全部通过，才进入阶段 7.1 的最小适配层设计。

当前阶段状态（2026-09-23）：已完成普通单角色入口、教程标记分支、`START_MAP`/`FINISH_LOADING`、合法与非法 `MOVE_MAP`、教程回城及断线不自动恢复的真实样本。组队、技能、战斗、结算、奖励和显式 rejoin 仍未验证，继续留在后续阶段；因此运行代码和 Web 能力矩阵不变，`dungeon_move` 仍为占位不支持。

#### 阶段 7.1：最小单角色地下城入口（后续）

- 仅实现已被阶段 7.0 证实的普通地下城单角色入口和加载闭环。
- 城镇移动与地下城移动使用不同接口、不同运行时状态和不同 PVF 查询；不把地下城房间坐标写入城镇位置快照。
- 组队、技能、战斗、结算和回城各自作为后续独立阶段；不因单角色入口成功而一次性开放全部能力。

阶段 7.1 的前置工作已开始：S4A21 协议层已加入经过真实探针验证的
`ENTER_SELECT_DUNGEON`、`SELECT_DUNGEON`、`CHANGE_TUTORIAL_FLAG` 和
`FINISH_LOADING` 原语及单元测试；适配层还增加了仅供内部使用的 run phase/generation 状态和已验证回包转换。上述内容尚未接入 `Session.MoveDungeon`、调度器或 Web。正式接入前仍需补齐失败、超时、回城和 Session drain 协调。

Session drain 协调的第一步已完成：S4A21 session 现在提供私有、可替换且可安全清理的 packet observer，单元测试覆盖真实 drain 转发和旧 observer cleanup；它仍不向共享层暴露原始封包，也不自动推进地下城能力。

本阶段对地下城结算与恢复的源码研究结论：普通副本通关至少还需要服务端通知 `ENABLE_CLEAR_DUNGEON (0x001F)`、客户端请求 `SET_PLAY_RESULT (0x002E)` 以及随后结算/回城通知；`SET_PLAY_RESULT` 的通用 A21 处理会读取 body 偏移 10 的客户端评级字段，但这不足以推断完整请求体或奖励语义。断线恢复使用独立的 `REJOIN_DUNGEON (0x02E0)`，请求体固定为 8 字节（partyId 与目标参与者 ID），并依赖服务端保留的副本/队伍状态；单角色、重启后和无 party 场景尚未形成可复现证据。因此当前实现不添加结算、奖励、回城或 rejoin 的共享能力，继续保持 `backend_capability_unsupported`，待真实抓包和端到端回归后再拆分接入。

本轮真实探针还验证了 `DIE_MONSTER (0x0027)` 的最小两字节 local index 请求以及 `BOSS_DIE_CHECK (0x0075)` 的四字节请求形状，服务端分别回发 `DIE_MONSTER (0x0026)` 并记录 boss 检查。但整合包中普通副本 144、145 的服务端日志均明确记录 `has no [clear condition]`，即使房间移动和击杀上报成功，也不会产生 `ENABLE_CLEAR_DUNGEON`。因此不能用这两个副本推断通关结算协议；下一步应先找到带有效 clear condition 的副本/任务状态，再进行真实结算回归。

源码自测还确认故事副本 160 的 clear condition 来自 PVF maze 与活动任务：maze 2/4/6 才带销毁对象条件，当前新建角色没有对应 active quest 时服务端会选择 maze 1 并同样记录无 clear condition。由于模拟端禁止直接修改游戏数据库，后续若要验证结算，必须通过任务/角色协议建立合法任务状态，或选择无需任务前置且确实带 clear condition 的副本；不能把数据库改写或“强制通关”探针作为适配实现。

任务协议探针确认：`ACCEPT_QUEST (0x001F)` 的请求体在服务端去除前 2 字节 echo 后，至少包含一个 little-endian `uint16 questId`；成功或失败都会返回同 opcode 的 ACK。登录/选角阶段的 `NOTI 0x0015 ACCEPTABLE_QUEST_LIST` body 以角色等级开头，随后是 `uint16` 数量和对应 quest ID 列表。对新建 1 级枪手直接请求故事任务 1844，服务端返回限制错误并记录 `character restrictions`，因此后续只能从服务端实际下发的可接受列表选择任务，不能猜测或伪造任务状态。
