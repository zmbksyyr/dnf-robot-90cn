# 多后端适配平台计划

## 目标

将 `dnf-robot` 维护为一个支持多个服务端实现的平台：调度、Actor 生命周期、机器人公共行为、运行时管理和 Web 管理共用；原生端、S4A21 以及未来的其他模拟端通过各自的适配实现接入。

第一目标是接入 `ServerS4A21`。本计划不要求一次性重写现有系统，也不引入通用插件市场、跨数据库模型或没有实际复用证据的抽象。

## 固定约束

- 环境由 Web 显式选择，启动时不根据路径、进程、端口或操作系统自动猜测并切换。
- 切换环境会停止机器人和会话，备份并重新初始化 robot runtime/config，再启动目标环境。
- 原生端当前仅支持 Linux，现有补丁、密钥、MySQL、`df_game_r` 和外围服务逻辑保留在原生适配边界内。
- S4A21 以及未来模拟端不得直接读取或写入游戏数据库，不区分 SQLite、MySQL 或其他存储实现。
- 模拟端账号、角色、装备、库存和货币变更只能通过对应服务端协议完成。
- 调度层和 Web 层只依赖契约与能力快照，不依赖具体后端包，不散落后端名称判断。
- 新增或删除某个后端时，公共调度和 Actor 层应保持可编译、可测试。

## 分层方案

保持现有项目分层，仅在确有边界的位置增加适配契约：

```text
foundation / shared
        -> backend contracts
        -> capability / actor
        -> protocol primitives and backend protocol implementations
        -> composition
        -> scheduler
        -> entry / webadmin
```

后端实现按垂直边界组织，而不是把所有差异塞进一个公共包：

```text
backend/
  contract/       # 接口、环境信息、能力、端点和不支持结果
  registry/       # 注册和构造当前可用后端
  native/         # 原生 Linux 服务端
  sim_a21/        # S4A21 模拟端
  sim_<future>/   # 后续模拟端
```

协议公共封包、校验和加密继续复用现有 `internal/protocol/dnf`。只有经验证存在差异的登录、角色、动作或副本处理才放入对应后端协议目录；没有差异的实现保持共用。

## 后端契约

契约只覆盖调度器实际需要的能力，初期包括：

- 环境元数据和支持的操作系统
- Game/Channel/Party 等端点
- 登录准备、账号/角色协议流程
- 缓存失效和服务健康检查
- 邮件、市场、组队等可选外围能力
- 能力快照和明确的不支持结果

契约不得暴露模拟端数据库句柄、数据库路径或 SQL 操作。原生端已有的 MySQL 登录准备也应逐步收拢到 `backend/native`，避免通用调度层继续持有原生 SQL 假设。

## 环境选择与切换

增加持久化的当前环境选择和配置代次。Web 提供：

- 可用后端列表
- 当前后端、根目录、端点和运行状态
- 支持的能力及禁用原因
- 显式切换操作和切换结果

切换流程固定为：校验目标配置 -> 停止 Actor/会话/调度 -> 保存审计和备份 -> 重建目标 runtime/config -> 构造后端 -> 初始化公共组件 -> 启动调度。切换不能静默迁移游戏数据，也不能复用另一后端的密钥、PVF 或状态文件。

## S4A21 第一阶段范围

S4A21 适配只通过网络协议与服务端交互：

1. 建立 Game/Channel 登录和角色选择流程。
2. 验证协议是否提供账号和角色创建路径；若缺失，记录为服务端协议能力缺口，不以改库绕过。
3. 接通进城、移动、喊话和基础重连。
4. 按协议能力逐步接入装备、商店、交易、组队和副本动作。
5. 对不提供的 Auction、Point、原生登录修复等功能返回明确的不支持状态。

S4A21 适配代码不得依赖其整合包使用的数据库类型，也不得读取 `inventory.db` 或其他服务端数据库文件。

## 实施阶段与提交边界

### 阶段 1：项目规则与计划

- 更新项目级 `AGENTS.md`，写入多后端、分层、协议优先和环境切换约束。
- 提交：`docs: establish multi-backend adapter rules`

### 阶段 2：契约和后端装配骨架

- 增加最小 backend contract、能力类型和 registry。
- 将现有原生启动装配包进 native backend，保持行为不变。
- 增加架构测试，阻止 scheduler/entry 直接依赖具体后端。
- 提交：`refactor: introduce backend contracts`

### 阶段 3：显式环境选择

- 增加当前环境持久化、Web 选择接口、切换生命周期和 runtime 重建流程。
- 先支持 native 与空的模拟端占位能力，验证切换不会污染公共状态。
- 提交：`feat: add explicit backend selection`

### 阶段 4：S4A21 协议适配

- 增加 S4A21 bundle 和必要的协议实现。
- 复用公共封包/密码代码，只实现实际差异。
- 接通登录、选角、进城、移动、喊话和重连测试。
- 提交：`feat: add s4a21 protocol backend`

### 阶段 5：调度和能力矩阵

- 将公共调度动作接入 backend contract。
- Web 根据能力快照禁用不支持功能并显示原因。
- 完成协议建号/建角能力验证；缺口保留为显式错误。
- 提交：`feat: route robot scheduling through backend capabilities`

### 阶段 6：功能扩展与回归

- 按 S4A21 实际协议能力接入商店、交易、组队、副本等功能。
- 原生 Linux 运行、部署和现有功能回归。
- Windows/Linux S4A21 运行验证。
- 每个独立功能按主题单独提交，不合并无关重构。

## 验证要求

每阶段至少运行相关 Go 测试和 `git diff --check`。后端必须通过统一的契约测试；S4A21 额外验证不得导入数据库驱动、不得访问服务端数据库文件。环境切换测试需覆盖停止旧会话、重建 runtime、能力刷新和失败回滚/保留诊断信息。
