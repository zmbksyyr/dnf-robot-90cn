# S4A21 能力状态

本文档记录当前仓库对应的 S4A21 模拟端能力边界。状态只描述本仓库已经实现的代码和已完成的验证，不代表服务端本身具备同名功能。

## 已实现并验证

- Robot 初始化、角色发现、角色认领和目标在线人数调度。
- 假人登录、保活、退出和重连。
- 城镇坐标解析、城镇移动和区域切换。
- 普通喊话/区域喊话，以及喊话模板和间隔调度。
- 角色删除、清理和 Robot 账号/角色身份维护。
- 角色等级、名字模板、职业与性别匹配。
- 装备、左右槽、装扮、宠物和宠物装备的生成与持久化；二进制字段与 GM 工具 codec 对齐：99B item core（kind/id/value/attr/durability/marker16=-1/选项变更索引=0xFF）、装扮详情 30B 宝石孔、宠物 `field04=100`（存活）、`field_after_value=1`（等级）、`creature_buffer` 保持为空（名称卡窗口）。
- 尽量成套、尽量多样、按职业过滤的装备和装扮穿戴逻辑。
- 真人邀请假人入队，假人自动接受邀请。
- 假人在城镇中跟随队长移动（队长位置/区域投影 → `SET_USER_POSITION` / `SET_USER_AREA`）。
- 队伍状态变化、真人退出或踢出后，假人退出跟随并恢复普通调度。
- Web 配置、调度、可见角色选择操作和 SQLite 只读统计审计。

## 已实现但不完整

- 工会邀请自动同意已实现，并已接入 S4A21 包解析；工会完整管理、主动申请、退出和更多事件处理尚未覆盖。
- 组队跟随只保留“跟随真人队长”的城镇投影部分（`USER_POSITION` / `USER_AREA` → `SET_USER_POSITION` / `SET_USER_AREA`）；假人主动建队、主动邀请、战斗、技能、结算和回城不在当前范围内。
- **副本内跟随不实现**（2026-09-28 结论）：副本房间位置只走客户端 UDP 数据面，而本环境客户端不处理成员的 UDP 位置帧，服务端也不向副本内队员投影位置；机器人因此只保留 TQOS 传输应答与 `SET_UDP_IP_PORT` 端点注册（组队界面不显示“连接中”），不解析/不发送应用层位置帧，也不再记录任何 `S4A21_PARTY_UDP_*` / `S4A21_FOLLOW_TRACE_*` 调试日志。
- 清理和危险删除已实现，但危险删除属于适配层 SQLite 操作，只针对明确的 Robot 身份，不用于普通调度缩容。
- 新角色的转职/觉醒已实现：创建后离线写入按 PVF 选出的转职分支与配置的觉醒档位（`grow_type`），并清空技能等待服务端在选角时按新状态重建；只提供存在 `[growtype N]` 成长段的转职分支。
- 角色等级写入已与经验、战斗属性对齐：按 `character/ExpTable.tbl` 写入该等级的累计经验阈值，并按服务端 `CharacterStatComputer` 相同算法（初值 + 14 级内基础段 + 转职段 + 觉醒段 + 特权生命/魔法加成）重算 `character_subtype1_fields` 各 `stat_*` 列；等级、经验、成长与属性在同一事务提交，客户端不再依赖服务端启动时重算。PVF 成长段缺失时使用零成长兜底表并通过启动日志 `S4A21_STAT_FALLBACK` 输出。
- 存量机器人的转职对账已实现：启动扫描后自动为仍未转职（`grow_type` 低 4 位为 0）且职业存在已开放转职分支的角色补齐转职与配置的觉醒档位；已转职但未觉醒的角色在 `[create] reconcile_awakening = true`（默认）时按 `grow_types` 中的正档位补齐觉醒；已匹配配置的角色保持原样；对账写入成长后同步重算战斗属性。
- 启动清理按明确规则执行：只认账号名严格等于 `前缀+UID` 且 UID 落在 `robot_uid_start..robot_uid_end` 的账号；这些账号若不是一个完整可用角色（角色数量、删除标记、等级窗口、职业、成长编码、装备/装扮/宠物窗口任一不符）则整账号删除，角色行级联删除。范围之外的账号与其他前缀账号不触碰。删除与扫描分离：先只读扫描，再在短事务内批量复核后删除（至少复核账号名、UID 与角色集合未变化），已修复的候选会被跳过。删除痕迹有界输出：`STARTUP_INVENTORY_DELETE`（默认最多 50 条，含账号/UID/角色数/原因）、`STARTUP_INVENTORY_DELETE_MORE`、`STARTUP_INVENTORY_SKIP_CHANGED`。
- 任务门禁已清空：启动时为每台机器人清掉原有任务行并写入固定门禁集合（世界地图持久门禁任务标记完成、`[in progress]` 与地城 `[quest connection]` 任务保持进行中），新角色在初始化时同样处理。机器人不再受任务门禁阻挡，也不再镜像任何来源账号。
- 任务门禁同时覆盖 QST `[dungeon info]` 反向引用：对没有 `[quest connection]` 的 `quest/`、`dungeon/quest/` 地城，会激活一个在 `n_quest/quest.lst` 中按 `[dungeon info]` 二元组引用它的任务（与服务端 `QuestTargetIndex.ReferencesDungeon` 同口径）。进行中任务超过 30 个时槽位继续向上分配：服务端准入与迷宫选择读取全部行，客户端 30 个固定槽由服务端按世界地图任务卡投影填充，与槽位数量无关。本机 PVF 实测连接任务已覆盖 6 个无连接任务地城；3 个地城（521/523/307 deadmoon、moonlight 变体）在本版本没有任何任务引用与地城连接，服务端本身即拒绝进入。
- 任务门禁只覆盖副本准入相关的任务状态，不实现机器人自己接取、推进或交付任务；等级、门票、次数、安徒恩权限等其他队员校验仍按服务端结果处理。
- 分解机（Disjoint/分解师摆摊）已接入适配层：机器人离线后由 `DisjointProfessionWriter` 写入 `character_subtype0_fields.expert_job_type=3`、`expert_job_exp>=800`，并把 `character_expert_job` 重置为 1 级 / 300 耐久（PVF `[endurance initial value]`）；重新登录后经 `SET_USER_AREA`/`SET_USER_POSITION` 走到选点，发送 `CREATE_EXPERT_JOB_STORE (0x0257)`（kind=0，费用 500 ≤ PVF `[limit store charge]` 10000），由 `CREATE_EXPERT_JOB_STORE (0x021B)` 通知 / `CLOSE_EXPERT_JOB_STORE (0x021C)` 通知和直接回执投影 `RuntimeStatus.RobotType=3`、`DisjointCreateSent/DirectAck/Active/LastDisjointError`；会话状态机在 `internal/composition/backend/s4a21/disjoint_store.go`，展示与选点仍归共享摆摊协调器。服务端 82（NPC 商业禁区）和 190（点位不可用/已开店）按同会话换点重试，其他错误码停止当前角色。
- 分解机的登录/清理接入了共享在线门控：离线写职业前等待 `waitAccountOffline`（A21 无 NoCache 指令，会话关闭即缓存边界，由 `protocolSessionDriver.CharacterCacheBoundaryIsSessionClose` 声明），重登录经在线令牌桶，清理走 `offlineStoreSession` + 正常位置恢复。

## 未实现或明确置空

- 拍卖行。
- 金币寄售。
- 个人摆摊商店（item stall）：S4A21 只实现分解机，未实现 `Robot_stall`/权限与库存离线准备，`ItemStoreSupported()=false` 让调度不再交替进入该分支；附魔店也未实现。
- 邮件通知轮询。
- 系统公告传输。
- 世界喊话/喇叭；当前使用普通区域喊话。
- 主动地下城移动、技能释放、战斗、战斗结算和回城。
- S4A21 专用诊断、服务控制和 party debug。

上述能力必须通过适配器返回明确的 unsupported 结果，Web 页面应隐藏或置灰，不能由公共调度层伪造成功。

## 尚未验证

- Linux 环境下的完整实机运行周期：初始化、PVF/SQLite 读取、登录调度、组队跟随、停止和再次初始化。当前分发包保留 `cmd/robot/main.go` 的 Windows-only 入口检查（防商用），Linux 可执行文件需要移除该检查后才能启动。
- Linux 下实际 S4A21 服务端地址、端口和数据库路径组合。
- Windows/Linux 长时间高在线人数运行下的连接稳定性和资源上限。
- 新角色转职/觉醒离线写入后的实机表现：客户端职业名与觉醒名显示、技能面板重建、战斗属性面板数值（离线算法已按服务端实现，客户端显示仍需实机确认）。
- 任务门禁清空后的实机组队结果：机器人队员通过普通/剧情副本的准入与地图进入表现。
- 分解机实机验证：开户回执/通知、服务端耐久扣减、到期或失败后的关闭与重新上线，以及高在线人数下分解机动作对服务器选角延迟的影响。

## 构建支持与运行支持

- Windows 和 Linux amd64 都支持构建与交叉编译；CI 在 ubuntu-latest 上执行 `go vet`、全量测试与 Linux 构建，防止 Linux 专属源码腐化。
- 运行支持当前只开放 Windows；`ensureWindowsRuntime` 是有意保留的入口限制，移除后 Linux 复用同一套源码与生命周期。
- `descriptor.go` 的 `SupportedOS` 表示构建/能力支持范围，不代表当前分发形态允许运行。

## 维护规则

- 新增或修复 S4A21 能力时，同步更新本文档和 `internal/composition/backend/s4a21/descriptor.go`。
- “已验证”必须有可复现的服务端/客户端验证记录；仅编译通过只能标记为“已实现”或“未验证”。
- 后续适配其他模拟端时复制适配层和对应能力文档，不得把 S4A21 的能力状态写入公共调度、Actor 或 Web 判断。
